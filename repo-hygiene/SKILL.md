# Гигиена репозитория

Отвечай на языке пользователя.

## Зачем

Самые дорогие ошибки в работе с репозиторием — не конфликты слияния, а тихие
рассинхронизации: работа идёт в одной копии, пуш уходит из другой, важный файл
годами лежит untracked. Проверка занимает секунды и ловит именно это.

## Проверка 1. Сколько клонов

Главная ловушка. Если копий репозитория несколько, работа и пуш легко
расходятся по разным папкам.

```bash
find ~ -maxdepth 4 -name .git -type d 2>/dev/null | sed 's|/.git$||' | while read d; do
  printf "%s\n  remote: %s\n  HEAD: %s\n" "$d" \
    "$(git -C "$d" remote get-url origin 2>/dev/null)" \
    "$(git -C "$d" log --oneline -1 2>/dev/null)"
done
```

Одинаковый `remote` у двух папок — повод сразу спросить пользователя, какая
рабочая, и предложить удалить лишнюю. Перед удалением проверить, что в лишней
копии нет незакоммиченного.

## Проверка 2. Отставание от origin

```bash
git -C <клон> fetch origin --quiet
git -C <клон> status -sb | head -1
git -C <клон> log --oneline HEAD..origin/main
```

Если локальная ветка позади — предложить `git pull origin main` до того, как
что-либо править.

## Проверка 3. Что не закоммичено

```bash
git -C <клон> status --porcelain
```

Разобрать вывод по смыслу, а не списком:

| Что видно | Что это значит |
|---|---|
| `??` на рабочем документе | важный файл никогда не коммитился, существует в одном экземпляре |
| `??` на `.DS_Store`, `Thumbs.db` | системный мусор, нужен `.gitignore` |
| `??` на `~$имя.docx` | файл-замок Word: документ открыт или Word падал |
| `??` на папке с `.git` внутри | чужой репозиторий вложен в ваш |
| `M` на файле в зеркале чужого проекта | правка потеряется при обновлении апстрима |

Untracked-файл с рабочим содержимым — не мусор. Показать его отдельно и
спросить, добавлять ли в git: у него нет ни истории, ни резервной копии.

## Проверка 4. Мусор и .gitignore

```bash
cat <клон>/.gitignore 2>/dev/null || echo "нет .gitignore"
```

Минимальный набор для macOS с документами Office:

```
.DS_Store
~$*
*.tmp
```

## Проверка 5. Бинарники в истории

```bash
git -C <клон> ls-files | grep -iE '\.(docx|xlsx|pptx|pdf|zip|png|jpg)$'
```

Бинарь в git не даёт читаемого диффа и не мержится. Для документа, который
регулярно правится, предложить markdown, а бинарную версию оставить как
экспорт. Не настаивать: если документ ведётся в Word, markdown ему не замена.

## Проверка 6. Вложенные чужие репозитории

```bash
find <клон> -mindepth 2 -name .git -maxdepth 3 2>/dev/null
```

Папка-зеркало чужого проекта внутри вашего репозитория — нормальная практика,
но в неё нельзя класть своё. Проверить, нет ли там ваших файлов.

## Формат вывода

Короткий список найденного, отсортированный по опасности: сначала то, что
может привести к потере данных (единственная копия файла, расходящиеся клоны),
затем неудобства (мусор, бинарники). К каждому пункту — одна команда для
исправления.

Если всё чисто — сказать одной строкой, не расписывать проверки.

## Чего не делать

- Не удалять и не коммитить ничего без явного подтверждения.
- Не предлагать `git clean`, `git reset --hard`, `checkout .` и прочие
  разрушительные команды при разборе untracked-файлов.
- Не считать любой untracked-файл мусором.
